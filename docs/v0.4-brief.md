# v0.4 — Window system, chrome, EQ, analyser

The biggest milestone in the project, and the one every earlier decision was
shaped to make possible. `windows.md` suggests splitting it, and that's right:

| | Scope |
|---|---|
| **v0.4a** | The window system. Bonding, splitter, shade modes, grouped z-order, layout persistence |
| **v0.4b** | The chrome and the audio graph. Eyewall from tokens in CSS (D72), EQ, analyser, viz stream |

They're separable, and the second is much easier once the first is proven. Don't
start 0.4b until 0.4a holds.

---

## Stage 6 is done. O17 is answered, and the answer was "no reshaping".

Ran 2026-08-31 across a 100% / 150% boundary. Checks 1–3 pass: a bonded group
crosses the seam and returns **bit-identical**, bonds survive, offsets stay exact,
and a bond forms cleanly between a window at `sf=1` and one at `sf=1.5`. Check 4 (monitor disconnect) was then tested with a real cable-pull — **all four checks pass** (D57–D59).

**`bond.rs` needs no changes.** Verified by diff, not asserted: it is byte-identical
to the stage-5 commit, all 34 tests green, and every one of stage 6's 713 changed
lines is in the disposable harness. Port it as-is.

The prediction behind O17 was wrong, and the reason is worth carrying: `bond.rs`
works in physical **virtual-desktop** coordinates, which are global and continuous
across monitors. Flush is flush at x = 2560 the same as anywhere else, so monitors
are simply not a concept the geometry needs. The one DPI-dependent quantity — the
threshold — was already an *input*. The physical-pixel convention paid for itself
exactly where it was supposed to.

**What the caller must now do (D51):** resolve *rendered geometry* from the
window's own monitor, and *interaction thresholds* from the monitor under the
**cursor**. Both get handed to `bond.rs` as plain physical pixels.

---

## What ports, and what doesn't

**Ports:** `src-tauri/src/bond.rs` and its **34 tests**. Pure geometry — no Tauri,
no Win32, no I/O, no globals. It is 100% of the correctness work and 0% of the
platform risk, and it is the only reason the spike repo still exists (D45).

**Does not port:** everything else in the spike. It was a measurement rig and it
was deliberately allowed to be sloppy — hardcoded colours, scattered `#[cfg]`,
`unwrap()` everywhere. Rebuild against this repo's rules, using the findings.

## The findings that are now requirements

These came out of the spike as measurements, not opinions. Each one is cheap to
honour up front and expensive to retrofit.

| | What it means for the build |
|---|---|
| **D37** | Assert per-monitor-v2 DPI awareness at startup with `AreDpiAwarenessContextsEqual`. Tauri ships **no** `<dpiAware>` manifest; awareness comes from a silent four-rung fallback in tao. Ship an explicit manifest too |
| **D38** | Declare window sizes in `PhysicalSize`, never the logical config keys. `275 × 1.5 = 412.5` and the toolkit picks the rounding |
| **D40** | **Round once, from logical.** Never scale, accumulate, or double an already-rounded physical value. Applies to the snap threshold, the 25/29 resize steps (D30), sprite rects, and the drag loop (`original + total_delta`, never `current + frame_delta`) |
| **D41** | **Hidden-root ownership** for bond groups. A never-shown window owns every member, so no real window is pinned to the back of its own group. Measured across six topologies; the others all fail |
| **D42** | Ownership applies **lazily**, on next activation. A bond break needs a forcing `SetWindowPos(SWP_NOMOVE \| SWP_NOSIZE \| SWP_NOACTIVATE)` or the z-order is stale-but-plausible until the next click |
| **D43** | Build **every** window `resizable(false)`, including the playlist. An undecorated resizable window gets an invisible `TAURI_DRAG_RESIZE_WINDOW` overlay that hit-tests above the webview in an ~8 px band — exactly on top of the bond seam. `set_size()` still works |
| **D44** | The Windows surface is **four calls**. Put them behind a trait now (the parent-project rule the spike was exempt from) |
| **D35** | The cursor tells the truth: splitter cursor only where a neighbour is resizable |
| **D30** | Playlist resizes in 25 × 29 steps on a 275 × 116 base |
| **D33** | Geometry **and the bond graph** persist across restart, physical px, monitor recorded |
| **D51** | Geometry from the window's monitor; interaction thresholds from the **cursor's** monitor. Caller resolves both; `bond.rs` takes physical px |
| **D52** | **Set position, then size.** Crossing a DPI boundary is not a pure move — tao rescales to preserve logical size, and size-then-position leaves a window 1.5× too big. A bonded group's geometry must be re-derived when it crosses |
| **D53** | A shared monitor edge is **not** a screen edge. Push each shared edge out to the far side of its neighbour, leaving only the desktop's genuine outer edges |
| **D54** | **Never hold the state lock across a Win32 call targeting another thread's window.** It deadlocks hard — cross-thread `GetWindowTextW` sends `WM_GETTEXT` and waits for the owning thread. Compute a plan under the lock, drop it, then call |
| **D55** | Cache the monitor topology. `monitor_from_point()` from a sync command deadlocks; topology changes about once a day |
| **D56** | Grouped raise **cannot** beat another process's foreground window. Qualifies D45: z-order within the app is real, raising above an unrelated app is not available without stealing focus |
| **D57** | Handle `WM_DISPLAYCHANGE`. Losing a display **minimizes** the group (`-32000,-32000`, `IsIconic=True`, but `IsVisible` stays true). Un-minimize, re-derive monitors, translate onto a surviving display. `scale_factor()` goes stale; `refresh_monitors` does not |
| **D58** | **Validate the graph against the OS, not itself.** It stays perfectly self-consistent while describing a layout that exists nowhere. `model/os agree` is the real health check |
| **D59** | `skipTaskbar` + undecorated + minimized = **unrecoverable**. The classic windows are undecorated by design, so this constraint is permanent |

**A stranded group needs rescuing (D57).** Losing a display minimizes the group
rather than relocating it, and nothing recovers it. The nearest-monitor rule
restores it as a rigid translation with zero bond violations — v0.4 needs that
**on startup and on `WM_DISPLAYCHANGE`**. Note the spike's own caveat: this was one
machine and one GPU driver, and other drivers reportedly *move* windows instead.
Build for both; the failure mode they share is that nothing reacts on its own.

**Test the interaction the way a user performs it, at least once per stage.** The
spike's scripted splitter sweeps passed at 0 px error while the real interaction
was completely dead, because an invisible window was eating the clicks. That is
how D43 was nearly missed.

## v0.4a — the window system

Three undecorated 275 × 116 windows (main, EQ, playlist), plus the shade states.
The video window already exists from v0.3 and stays outside the bond group (D13).

- **Entry points.** The frontend is plain Vite specifically for this: add
  `main.html`, `eq.html`, `playlist.html` next to `index.html` and `video.html`,
  wired in `vite.config.ts` under `build.rollupOptions.input`. Windows are not
  routes
- **Focus is a group property.** When any bonded window has focus, all of them
  render active. Getting this wrong looks broken immediately
- **Shade modes** — 275 × 14 each. The Main shade doubles as the always-on-top
  mini-player and is, per the design brief, the single most important screen in
  the project
- **Persistence** — `window_layout` and `window_bonds` tables already exist in the
  schema (D33), unused so far

## v0.4b — chrome from tokens, EQ, analyser

- **Chrome is drawn from the six tokens in CSS** (D71, D72). `design/sprites/`
  and `skins/eyewall/` are both empty, so there is no sheet to render and no
  pipeline that would produce one; the three classic windows get their chrome
  from `tokens.json` instead. The cost is stated in D72 rather than discovered
  later: the chrome gets written twice, and the sprite path is proven in a
  later milestone
- **`hp-skin/1`** is specified in `skin-manifest.md` (D36) and stands
  unchanged. Both importers are mappings *into* it, so it is load-bearing for
  v0.5 — and D72 defers *proving* it against a real layout, not the schema.
  Deriving fixed rectangles from the flexbox prototypes in `design/screens/`
  is the first genuine test of whether the schema is expressive enough; that
  work moves with the sprite path. The prototype is not the spec; where they
  conflict, the spec wins
- **EQ** — 10 bands per D21, `.eqf` mapping per D31 (**inverted**: `0x00` = +12 dB,
  and the preamp byte is **last**). Trim gain after the chain plus a clip
  indicator; a `DynamicsCompressorNode` is the lazy option and it colours the sound
- **Analyser** — spectrum bars on the 24-entry radar ramp from `design/tokens.json`.
  The analyser's glow is **pre-rendered in its ramp art**; no CSS filter on the
  visualizer or any ancestor of it (D73). Chrome glow is the renderer's, from tokens
- **Viz stream** — binary frames on a separate pipe (`control-api.md`). `hello`
  currently advertises `["transport"]` only; this adds `"viz"`

### Measure the viz latency before it goes anywhere near v1.0

`control-api.md` is explicit: the analyser lives in the webview (D5), so the
spectrum path crosses the IPC boundary. Target is **under 20 ms speaker-to-socket**.
Measure it. Once someone's LED rig is calibrated against the timing you cannot
quietly change it — and if it comes in worse, the fix is moving analysis into Rust
with `symphonia`, which is a much bigger change and better known about early.

## The bond seam is the one animated moment

Four states — idle hairline, hover (+1 px), dragging, and a ~120 ms discharge
bloom on break. Everything else in the interface stays still; spend the boldness
here and nowhere else. `prefers-reduced-motion` makes the discharge an instant
state change. Animate `opacity` on a pre-composited layer, never `box-shadow`.
