# Decision Log

Authoritative. When anything contradicts this file, the other thing is wrong or stale.

**Append, don't rewrite.** Superseded decisions get struck through with a pointer to what replaced them, so the reasoning survives.

**Provenance.** These rows were drafted in planning sessions with Claude. Some are the owner's business requirements; others are recommendations the owner accepted at the time. Where a decision conflicts with a business requirement the owner states, **the requirement wins**, and the fix is a superseding row (`/decide`) so the log stays true, rather than a silent contradiction in the code. Rows from D65 on say which they are: **(req)** or **(adv)**. Tagging D1–D64 is tracked as a GitHub issue.

| D48 | ffmpeg build size | **Deferred to v0.6, deliberately.** The dev machine's full build is 231 MB per binary (462 MB with ffprobe), against an architecture doc that pitches Tauri partly on "~10 MB vs Electron's 150 MB". v0.1 wires the sidecar plumbing with a minimal build to prove the mechanism; the shipping build is chosen when packaging actually matters. **The wiring is identical either way**, so this blocks nothing now — but it is a real decision, not a forgotten one, and the lightweight claim is on the line |
| D49 | On-disk layout | **`<root>/%(extractor)s/%(title)s [%(id)s].%(ext)s`** — grouped by source, flat within it. `architecture.md` originally nested by `%(uploader)s` too; that is dropped, because on YouTube the uploader is the **channel, not the artist**, and it produced roughly one folder per file. The value is still captured on `media.uploader`, and the library browser is a DB query (O6) rather than a directory listing, so the filesystem does not have to be the navigation surface. The trailing `[id]` is load-bearing: it is how a resumed job finds its own file without parsing yt-dlp's stdout |
| D50 | Local tag reading uses `lofty`, not ffprobe | `architecture.md` said "read tags via ffprobe". That would be a **fourth sidecar at ~98 MB**, against a bundle already carrying ~230 MB of helpers (D48) for a 10.8 MB application. `lofty` is a pure-Rust tag reader covering ID3v2, MP4, FLAC, Vorbis and WAV — it compiles in for effectively nothing and needs no process spawn per file, which matters when scanning a folder of thousands. ffmpeg stays the transcoder; it is just no longer the metadata reader |
| D51 | Two threshold rules, not one (**answers O17**) | The single-`threshold` argument felt wrong because **two quantities were conflated**. **Rendered geometry** — window size, the 14 px strip, minimum size — resolves from **the window's own monitor**: it is a fact about that window, and the strip really is physically taller on a 150% display. **Interaction thresholds** — snap distance, seam-grab radius — resolve from **the monitor under the cursor**: they encode a perceptual distance, and the user is looking at exactly one place. Both are resolved **by the caller** and handed to `bond.rs` as plain physical pixels. Measured discriminator: a 13 px gap across the boundary bonds when the cursor is on the 150% side (threshold 15) and does not when it is on the 100% side (threshold 10) — same gap, same windows, opposite outcome |
| D52 | Set position, then size | Crossing a DPI boundary is **not a pure move**: Windows sends `WM_DPICHANGED` and tao rescales the window to preserve its *logical* size. Size-then-position leaves a window 1.5× too big after a crossing (asked 413×174, got 620×261). Beyond the ordering bug this is a design consequence: a 275-skin-px window **should** be 275 physical at 100% and 413 at 150% so the chrome looks the same size on both — which means **crossing a boundary legitimately changes a window's physical size, and a bonded group's geometry must be re-derived when it does** |
| D53 | A shared monitor edge is not a screen edge | Screen-edge bonding snapped to x = 2560 — the *seam between two monitors* — and then refused to bond with a neighbour 8 px beyond it. The desktop continues through that seam; treating it as a wall strands windows there and makes cross-monitor bonding impossible. Each monitor edge shared with another monitor is pushed out to the far side of its neighbour, leaving only genuine outer edges of the desktop. Caller-side; `bond.rs` untouched |
| D54 | Never hold the state lock across a Win32 call targeting another thread's window | Caused a hard deadlock (process alive, `Responding: False`). A background thread held the lock inside `GetWindowTextW` on a main-thread window; cross-thread `GetWindowTextW` sends `WM_GETTEXT` and **waits for the owning thread**, which was waiting for the lock. `SetWindowPos` has the same shape. **Compute a plan under the lock, drop it, then make the Win32 calls.** Easy to violate by accident — the call looks synchronous and local, and is neither |
| D55 | Cache the monitor topology | `monitor_from_point()` from a sync `#[tauri::command]` deadlocks: the command already runs on the main thread and the API dispatches back to it. Topology changes roughly once a day, so cache it and resolving a monitor becomes pure arithmetic |
| D56 | Grouped raise cannot beat the foreground lock | `SetWindowPos(HWND_TOP, SWP_NOACTIVATE)` **cannot** lift a window above another process's foreground window — Windows' foreground lock. **This qualifies D45's z-order result:** stage 2's raise was partly cosmetic, and stages 3–5 only worked because their coordinates happened to lie in a region nothing covered. On a 6400 px desktop that stopped being true and the flakiness surfaced. Grouped z-order within the app is real; raising the group above an unrelated foreground app is not available without stealing focus |
| D57 | Handle `WM_DISPLAYCHANGE` — Windows **minimizes**, it does not relocate | Measured on a real cable-pull, not simulated. Losing the display a group is on leaves every window at `rect = -32000,-32000 160x28` with `IsIconic=True` — the classic minimized rect. **`IsVisible` stays `true` while minimized**, so a z-order walk still lists them, which is its own trap. On reconnect Windows restored position, size and scale factor exactly, bonds intact. v0.4 must un-minimize, re-derive monitors, and translate onto a surviving display; check 4a's nearest-monitor rule does this as a rigid translation with **0 bond violations**. Also re-sync after any topology change: `scale_factor()` went **stale** (windows still reporting 1.5 with only a 1.0 monitor attached) while `refresh_monitors` was correct immediately |
| D58 | Validate the graph against the OS, not against itself | **The deepest finding of the spike.** With the monitor gone, the bond graph stayed *perfectly self-consistent* while being completely disconnected from reality: `flush violations: none`, all bonds present, components correct — describing three windows bonded flush at 3000/3413/3826, a layout that existed nowhere. That is *correct* behaviour for a pure geometry module nobody told anything had changed, and it means **internal consistency is not a health check**. Anything validating the graph against itself would have reported everything fine. The reconciliation point is `model/os agree`, which went `false` immediately |
| D59 | Never ship `skipTaskbar` without another restore path | Minimized **+** `skip_taskbar: true` **+** `decorations: false` = no taskbar button, no titlebar, **no user-facing way to restore the windows**. If the display never comes back, the group is gone. The flag was a cosmetic stage-0 choice so three grey rectangles wouldn't clutter the taskbar; the hazard only exists in combination with an OS behaviour on a hardware event, and **neither decision looks dangerous alone**. The three classic windows are undecorated by design (D12), so this constraint is permanent, not incidental |
| D60 | Windowshade toggles on a title-bar double-click | Authentic: Winamp toggles windowshade on a title-bar double-click as well as through the titlebar button. The button needs `TITLEBAR.BMP` sprite regions that do not exist until v0.4b, so gating shade on it would have shipped geometry nobody could reach and no hand test could cover. The two do not collide — the seam already owns `dblclick` for demagnetize (D16), and the seam strip is a separate 4 px element stacked above the title bar, so the hit target decides which gesture fires. The sprite button lands in v0.4b **alongside** this, not instead of it |
| D61 | Always-on-top follows Main's shade, and takes the whole group | Shading the Main window makes every window in Main's connected component topmost; expanding clears it. Two halves. **Derived, not stored:** `window_layout.shaded` already persists, and there is no `always_on_top` column to drift from it. **Whole group, not just Main:** the three classic windows are owned by a hidden root rather than by each other (D41), so topmost is per-window and does not propagate — lifting only Main would split a bonded stack across the z-order, with Main floating above other apps while its own bonded neighbours sit behind them. `windows.md` frames the mini-player as windowshade *plus* always-on-top; this is that pair, with the group kept in one z-band |
| D62 | Display changes are detected by **polling**, not by a `WM_DISPLAYCHANGE` hook | D57 says "handle `WM_DISPLAYCHANGE`", and this handles the *situation* rather than the *message*. Tauri and tao surface no display-change event at all — tao consumes `WM_DISPLAYCHANGE` internally to refresh its own monitor list and re-emits nothing — so receiving it means subclassing a window proc across FFI, which is a new failure surface on the one path that has to work when a monitor vanishes. A 2 s poll compares the enumerated topology against the cache and checks `IsIconic`, on the main thread. **It is strictly more coverage, not a compromise:** it catches both driver behaviours D57's caveat names — the measured *minimize* and the reported *relocate* — and it also catches a group already stranded at launch, which no message would ever have been sent for. D55 measured topology as changing about once a day, so the interval is slack on purpose. The rescue is independent of the trigger, so a subclass hook can replace the poll later without touching a line of it |
| D63 | Closing **Main** quits the app; the satellites refuse to close | Found by hand, and it was not a nicety — **the app had no exit path at all.** Tauri exits when every window closes, and D41's three hidden roots are windows that are never shown and can never be closed, so that condition was unreachable. Closing Main from the taskbar destroyed only Main and left eq and playlist behind as undecorated windows with no taskbar button and no title bar: **D59's unrecoverable state, reached without a monitor ever being unplugged.** Two decisions that each looked safe — hidden roots for z-order, `skipTaskbar` on the satellites — combined into a process only Task Manager could end. So: Main's close saves the layout and exits; eq and playlist `prevent_close()` because nothing yet brings them back and a window that vanishes for good is worse than Alt+F4 doing nothing; the library window closes normally unless it is the last visible window, in which case it exits too. Matches Winamp, where closing the main window quits |
| D64 | Local folder import claims **video as well as audio** | Reverses a v0.3 scope call, on purpose. Local video was held back because it raised two questions the milestone had not answered — where it plays and what a thumbnail is. The first is settled: D13's decorated video window ships, and the library already routes a `kind = 'video'` row to it, so the wiring was complete and only the scanner had not caught up. Leaving it audio-only meant a downloaded video appeared in the library while **the identical file found by a folder scan did not** — which is how a real mp4 went missing after its `media` row was lost and the folder was re-added. Container list is deliberately narrow (`mp4 m4v mkv webm mov avi`) rather than "anything ffmpeg knows": a row that opens a window and then fails is worse than a file the library never claimed. Thumbnails remain unanswered and remain out of scope |
| D26 | Job resume semantics | **True byte-level resume, not restart.** yt-dlp `.part` files are preserved across a crash and re-invoked with `--continue`. `jobs` records the resolved output path and which `stage` it died in, because resuming a download and resuming an ffmpeg extract are different recoveries. D10's `running` → `queued` still applies; it means "re-enter the runner," not "start over" |
| D27 | Milestone authority | **The milestone table below is canonical.** `CLAUDE.md` and every other doc point at it. Duplicated milestone tables elsewhere have been deleted rather than maintained in parallel |
| D28 | Library roots and paths | Many roots from day one (was O8). A `library_roots` table; `media` stores **`(root_id, relpath)`, never an absolute path.** An external drive that comes back as a different letter must not orphan the library — which is the exact case multi-root exists to serve |
| D29 | Zero-network enforcement | A **tested property, not an aspiration.** The webview CSP forbids remote origins outright — no `connect-src`, `img-src`, or `font-src` beyond `self` and `asset:`. All egress lives in Rust behind a single allowlisted radar-fetch command (D19). A test runs the app with the interface down and asserts no connection is attempted |
| D30 | Playlist resize increments | **25 px horizontal, 29 px vertical**, on the 275×116 base. Valid playlist sizes are `275 + 25n` × `116 + 29m`. **Verified** against Webamp (`WINDOW_RESIZE_SEGMENT_WIDTH` / `_HEIGHT`). Closes the open item; the design prototype's `step:10` is off-spec and the spec wins |
| D31 | `.eqf` byte mapping | **Verified.** 31-byte signature (`Winamp EQ library file v1.1\x1A!--`), then a 257-byte name buffer, then **10 band bytes followed by the preamp byte** — preamp is last, not first. Values are `0..63` and **inverted**: `0x00` = **+12 dB**, `0x1F` = 0 dB, `0x3F` = **−12 dB**. Band order matches D21. A naive reader flips every preset upside down and lands the preamp on 60 Hz |
| D32 | Settings storage | A `settings` key/value table in the same SQLite file, not a side config file. Puts settings in the same WAL transaction domain as the library, so a hard power loss can't desync them |
| D33 | Layout persistence | Window geometry **and the bond graph** persist across restart, in physical pixels with the monitor identity recorded. Restoring a group onto a monitor that no longer exists must not strand it offscreen |
| D34 | `media` carries its own title | `media` denormalizes `title`, `uploader`, and `duration_s`. Local folder imports have `source_id NULL` (they have no source), so without this the library browser cannot render a row for a file the user already owned |
| D35 | Splitter on fixed-size pairs | **The cursor tells the truth** (`windows.md` option 3). The splitter cursor appears only on edges where at least one neighbor is resizable; elsewhere it's the move cursor and the drag moves the group. Nothing is inert, because nothing is offered. Costs one capability check at hover time |
| D36 | Native skin manifest | **`hp-skin/1`**, specified in `skin-manifest.md`. It is the format the default skin ships in and the target both the `.wsz` and `.wal` importers map *into* — so it is the load-bearing schema for v0.4 and v0.5 both. Per-window `resizable` capability, 9-slice regions, and a swappable `visualizer` component (D20) |
| D37 | DPI awareness is asserted, not assumed | Tauri does **not** declare DPI awareness in its embedded manifest — `tauri-build`'s `windows-app-manifest.xml` has no `<dpiAware>` element at all. Awareness comes from tao's `become_dpi_aware()`, a four-rung fallback ladder where every rung below the top is a silent `let _ =`. A v1 or system-aware fallback still reads `scale_factor() == 1.5` on a single monitor while breaking cross-monitor behaviour. **Ship an explicit application manifest, and keep a startup assertion** using `AreDpiAwarenessContextsEqual` — the `DPI_AWARENESS` enum cannot distinguish v2 from v1. Verified in the v0.0 spike |
| D38 | Window sizes are declared in physical pixels | `275 × 1.5 = 412.5`. A logically-sized window inherits a half-pixel that the toolkit resolves by its own rounding rule (tao rounds up, to 413). For a bond model whose premise is two windows sitting *flush* with a hairline seam, that means "flush" is defined by tao's rounding mode and a 1 px gap or overlap can appear in the most visually load-bearing place in the app. Use `PhysicalSize`, never the logical `width`/`height` config keys. Verified in the v0.0 spike |
| D39 | Drag smoothness criterion | The original "≤ 2–3 px trail at normal speed" was **wrong** — at 800 px/s it implies under 4 ms end-to-end, a quarter of a frame. Replaced by: **excess over floor** (mean lag − velocity ÷ event rate) **≤ 1 px at slow and normal speed**, cross-checked by **latency ≤ 1.1 frames**. Measured on the spike: 0.18–0.81 px excess, 17.2–17.9 ms (1.03–1.07 frames at 59 Hz). Trail in raw pixels is not a portable criterion — it scales with both velocity and refresh rate |
| D40 | Round once, from logical | **Extends D38.** Physical dimensions are derived from the logical source in a single step and rounded exactly once. Never scale, accumulate, or double an already-rounded physical value. Verified in the spike: `275 × 1.5` rounds to 413, but 2x chrome is `550 × 1.5` = 825, and `413 × 2` = **826** — rounding does not commute with doubling. Worse, it compounds: stepping the playlist by a rounded physical increment (D30's 25 logical px → 38 physical at 1.5) drifts **5 px from true after ten steps, 10 px after twenty, 20 px after forty** — unbounded, which walks a bonded neighbour progressively out of flush. The logical size is the source of truth; physical is recomputed fresh, never carried forward. **Applies to the drag loop too:** every frame computes `original_rect + total_delta`, never `current_rect + frame_delta` — accumulating per-frame deltas is the same error shape |
| D41 | Bond group z-order topology | **Hidden-root ownership.** Every member of a bond group is owned by a never-shown window; no real member is the owner. Measured across six topologies in the spike: this is the only one where *every* member can reach the top of its own group, because an owned window is always above its owner and clicking the owner cannot fix that — a star or chain topology permanently pins one window to the back of its own group. It also shrinks the D16 bond-break problem: splitting a group means creating a second hidden root and re-pointing children, not promoting a member and re-parenting everything around it |
| D42 | Ownership is applied lazily | Windows enforces the owned-above-owner invariant **on next activation, not when `SetWindowLongPtrW` returns.** Re-parenting a live window costs ~28–47 µs with no flicker, no z-position loss, and no activation change — but it also does nothing visible, leaving the z-order stale-but-valid-looking until the next click. A bond break that must look correct immediately has to force it with `SetWindowPos(SWP_NOMOVE \| SWP_NOSIZE \| SWP_NOACTIVATE)` after the re-parent |
| D43 | All windows are built `resizable(false)` | **Non-obvious and it silently eats the signature interaction.** For an undecorated *resizable* window, `tauri-runtime-wry` spawns an invisible `TAURI_DRAG_RESIZE_WINDOW` overlay (`undecorated_resizing.rs`) that hit-tests **above** the webview in a band of `SM_CXFRAME` + a 5-logical-px inset around the edge — measured at ~8 physical px at 150%. That band sits exactly on the bond seam, so it covers precisely the edges D35 makes interactive. `set_size()` still works on a non-resizable window, and the app does its own resizing through the splitter, so the native affordance was never wanted. Confirmed at the source: the helper no-ops when `WS_SIZEBOX` is absent |
| D44 | The Windows platform surface is four calls | Measured, not estimated. `SetWindowLongPtrW`/`GetWindowLongPtrW` with `GWLP_HWNDPARENT` (ownership — the real gap, since Tauri exposes `owner()` on *builders* only and has no `set_owner` on a live window), `SetWindowPos` with `SWP_NOMOVE\|SWP_NOSIZE\|SWP_NOACTIVATE` (D42), and the D37 DPI assertion. Everything else stages 0–5 needed was covered cross-platform and was already physical-first. **Much smaller than `windows.md` assumed** — the trait is a file, not a subsystem |
| D45 | v0.0 verdict — the bond model is GO | The spike answered every platform question yes, with numbers: drag costs one display frame and 0.2–0.8 px over floor; owned HWNDs group z-order and re-parent in ~40 µs with no visual disturbance; bonds form and break correctly through a real graph with zero drift over twenty group drags and zero seam error across 61 splitter steps in both model and OS. **D12 and D16 stand.** The one unanswered question is cross-scale (stage 6, O14). `bond.rs` + its 34 tests are the artifact that ports to v0.4; **the spike repo must not be deleted until that port happens** |
| D65 | Video letterbox colour | The bars around a video that does not fill its window are painted with the **`well`** token (`#05040A`, the deepest Eyewall colour) through the theme import, not a literal black. `src/Video.svelte` carried the one hardcoded hex in `src/` (`background: #000`), which the guard hook now refuses on any new line, and the question was whether that line is a theme surface or a recorded exception. It is a theme surface: the video window is decorated and outside the bond group (D13), but it is still the app, so the letterbox follows whichever theme is active (D18) and there is no `tokens-exempt` marker to remember. The road not taken was pure black with a marker, on the argument that letterboxing is conventionally black and a tinted frame around a film reads as a defect; rejected because on a dark-only app a near-black `well` is indistinguishable from black in practice, and keeping the non-negotiable absolute is worth more than the convention. Resolves the decision half of issue #13; the one-line code change is the rest of it **(req)** |
| D66 | `bond.rs` evolves under its tests; byte-identity with the spike is retired | D45 made byte-identity the proof that the port was complete, and the port is complete: the spike is archived, main first diverged by whitespace when rustfmt was adopted, and #12 made the first semantic edit (`map_or(true, ..)` to `is_none_or`, an identity). What #12 found is the reason this needs a row: mutating all three snap-cost comparisons to "keep whichever candidate came last" left every one of the 125 tests green. The 34 bond tests were never a guard for the comparison they sat beside; `the_nearer_of_two_candidates_wins` passed under three different rules because its cheaper candidate was also the last one probed. Two tests now pin cheapest-wins in both directions (a corner case at real chrome size in `bond.rs`, the swapped order in `wm.rs`), each confirmed by re-running the mutations, and the count is 35. So `bond.rs` is an ordinary module that changes under its tests, and "34 tests, byte-identical" is history, not a standing claim. Internal consistency is not a health check (D58); neither is a green suite until a mutation has shown it can fail **(adv)** |
| D67 | Dispatch into a webview is fire-and-forget | `eval`, `eval_with_callback` and `emit_to` all compile to a bare `send_user_message` in this build (`tauri-runtime-wry-2.11.4/src/lib.rs:1854`, `:1889`) and none of them carries a reply channel. `send_user_message` (`:235`) returns `Ok(())` on the main-thread path unconditionally and off-thread errors only when the event-loop proxy is dead; on the event loop a destroyed webview fails the `if let Some((Some(window), Some(webview)))` match at `:3751` and the message is **dropped silently**, while a genuine `evaluate_script` failure is `log::error!`'d and discarded at `:3773`. So **`Ok` from a command that dispatches to a webview means dispatched, never confirmed** — its error path fires only when the whole event loop is gone, which is app teardown, when there is no frontend left to show anything. The trap is that the *first* `eval_script` you meet reading the source, `:1839`, does return a real error through `getter!` — it is `#[cfg(feature = "tracing")]`, this build does not enable that feature, and so the arm you read is not the arm that ships. Confirmation requires a round trip: either a `getter!`-backed call such as `url()` (`:1661`), whose `rx.recv()` sees the dropped `tx` and returns `FailedToReceiveMessage` (`:197`), or an ack from the page itself. Cost PR #30, which added `?` to an `eval` that cannot fail, passed every gate, and fixed nothing. |---|---|---|
| O3 | Chrome scale steps | Integer only: 1x / 2x, default 2x. Never fractional — it makes sprite bitmaps mushy |
| O5 | Prep mode: own window? | Yes. Opened on demand, decorated, normal size. Not a wizard — it gets used under time pressure |
| O6 | Library browser shape | Flat sortable table with a filter box. Not a tree |
| O7 | Platform targets | Windows first. Keep code portable, don't test elsewhere until needed |
| O8 | Library roots: one or many? | Many, from day one. **See D28** for the path model this forces |
| O9 | Profiles | Skip the feature, but carry `profile_id` on `playlists`, `play_history`, and `jobs`, defaulting to 1. Free now, a migration later |
| O10 | Default storage cap | None. Show the meter, warn at 85% of free disk |
| O11 | yt-dlp updates | Pinned bundle plus an in-app "check for update." **Never silent auto-update** — a surprise yt-dlp bump the day before a storm is the wrong failure. Applies to the PoToken provider too (D25) |
| O12 | Download concurrency | Default 2, adjustable 1–4. Higher gets throttled, not faster |
| O13 | Does the Library window bond? | No. The bond group is Main + EQ + Playlist only — the three classic 275px windows |

## Still open

| # | Question | Status |
|---|---|---|
| ~~O17~~ | ~~`probe()` takes one snap threshold~~ | **Answered by stage 6 → D51, and the prediction was wrong.** `bond.rs` needed **no reshaping**: it is byte-identical to the stage-5 commit, verified by diff, with all 34 tests green. It survives because the physical-pixel convention does exactly what it was adopted for — the module works in physical *virtual-desktop* coordinates, which are global and continuous across monitors. Flush is flush at x = 2560 the same as anywhere else, so monitors are not a concept the geometry needs. The only DPI-dependent quantity is the threshold, and it was already an input |
| O16 | WebView2 blank-page flake at startup | **Observed once, unreproduced.** All three webviews came up on WebView2's error page with correct HWNDs but no JS running. Hypothesis: the DPI gate slept ~120 ms on the main thread, which is also WebView2's message pump, aborting navigation. Gate moved to a spawned thread, but **the fix is unproven** — 11 consecutive launches came up clean, including 5/5 on the *old* binary. Recorded as a flake with an unverified mitigation. First place to look if it recurs |
| O15 | Is the webview's input coalescing perceptible? | **Open, low priority.** The spike measured 14.1 px rect-level trail at 800 px/s, of which 13.3 px is the webview coalescing 125 Hz of mouse input down to one `pointermove` per frame. A native Win32 drag loop processing every message would trail ~4 px at rect level. Whether that ~10 px gap is *visible* is unknown — both present at 59 Hz, and photon-level latency was not measured (needs a camera). **Do not chase this now.** Revisit only if drag ever feels loose in real use, and answer it by building fallback 2 as a comparison rather than as a rescue |
| ~~O18~~ | ~~Monitor disconnect while a group is on it~~ | **Tested 2026-08-31 with a real cable-pull → D57, D58, D59.** The result was nothing like the offscreen proxy: Windows **minimizes** rather than relocating. Stage 6 now passes all four checks. **Caveat recorded by the spike:** one machine, one GPU driver — other drivers reportedly *move* windows instead. The lesson (silent divergence, nothing reacts) holds either way, so build for both |
| ~~O14~~ | ~~Second display for DPI validation~~ | **Resolved 2026-08-31.** A second display is now attached: **primary at 100%, secondary at 150%** — two live scale factors, which is exactly the case stage 6 needs and stages 0–5 could not reach. Stage 6 is unblocked and should run **before** `bond.rs` is ported, because O17 may reshape that module. See `v0.4-brief.md` |
| ~~O19~~ | ~~Which palette wins when a skin's differs from the theme's?~~ | **Resolved 2026-09-11 → D101.** A manifest carries `palette` and `viscolor` (D36) and the loader validates them, but the renderer tints from the theme's tokens and draws the theme's ramp; for Eyewall the two are the same file, and a test says so. An imported `.wsz` brings its own (`PLEDIT.TXT`, `VISCOLOR.TXT`), and a theme (Cone, Purricane) brings its own too. Skins are chrome, themes are palette and visualizer; whether picking a skin re-tokens the app or a theme re-tints a skin is one call to make before the first import, not two |

New questions get appended here and promoted to a D-number when resolved.
